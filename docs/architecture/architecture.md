# Architecture

Promptsheon is a single-binary HTTP daemon with a layered
internal structure. The Go module is one `package main` at the
repo root plus the implementation under `promptsheon/`. This page
describes the package layout, the migration timeline, and the
integration boundaries.

## Source layout

```
promptsheon/
├── main.go                   # Single entry point; dispatches by os.Args[0]
├── daemon.go, cli.go, ...    # All in package main; bin name picks mode
├── promptsheon/                  # Server-side implementation
│   ├── server.go, routes.go  # HTTP server composition + mux registration
│   ├── handlers_*.go         # One HTTP handler file per domain
│   ├── handlers_helpers.go   # validateNonEmpty, parsePagination, ...
│   ├── <pkg>/                # Domain packages (see below)
│   └── store/                # SQLite-backed Repository implementation
└── bin/                      # Build artefacts (promptsheond, promptsheon, promptsheon-healthcheck)
```

`main.go` switches on `os.Args[0]`:

- `promptsheond` → `runDaemon()`
- `promptsheon` → `runCLI()`
- `promptsheon-healthcheck` → `runHealthcheck()`

The three binaries are produced from the same source via
`make build` (which calls `go build -o bin/<name> .` three
times).

server composition and HTTP handlers. Files listed without a

## Migrations

The store schema is versioned by `promptsheon/store/migrations/*.up.sql`
files. The current schema applies migration `019_self_evolve.up.sql`
plus the destructive `008_destructive_cleanup.up.sql` (gated by
`PROMPTSHEON_ALLOW_DESTRUCTIVE_MIGRATIONS=true`).

To add a new migration, drop a `020_your_migration.up.sql` (and a
`.down.sql`) in `promptsheon/store/migrations/`. The next
`./bin/promptsheond` boot applies it.

## Storage backends

The daemon ships with SQLite (`modernc.org/sqlite`, CGo-free)
as the production store. There is no Postgres backend wired in
this build; the `store.Repository` interface in
`promptsheon/store/repo.go` exists so a future pgx-backed
implementation can be added without touching the domain
packages (ADR-0012). Operators that need a different store
today can satisfy that interface in their own fork.

## Provider registry

`promptsheon/llm/Registry` is the consumer-defined provider
registry. The daemon ships with **OpenAI** and **Anthropic**.
To add a new provider, register a factory on the `Registry`
at process startup (see `daemon.go`):

```go
r := llm.NewRegistry()
r.Register("myprovider", func(cfg llm.ProviderConfig) llm.Provider {
    return MyProvider(cfg)
})
```

The `Provider` interface (`Complete(ctx, *Request) (*Response,
error)`) is the integration boundary; an SDK adapter
implementing that interface is all that's required.

## Plugin supervisor

`promptsheon/supervisor.Supervisor` owns the plugin lifecycle:
restart budget, health gate, manifest-driven registration.
The default transport is in-process (`promptsheon/plugins/`); the
`subprocess` package provides net/rpc-over-UDS for plugins
that need isolation. A manifest entry without a working
plugin fails closed so operators see the gap in `/metrics`
rather than a silent healthy stub.

## Audit chain

The audit log is a **hash chain**, not an append-only list.
Each row records `previous_hash` (the rowid's predecessor's
`entry_hash`) and `entry_hash` (sha256 of the row's canonical
JSON). `store.VerifyAuditChain` walks the chain from rowid 1
forward and asserts the chain invariant.

`audit_archive` (migration 011) is the retention target:
rows older than `PROMPTSHEON_AUDIT_TTL_DAYS` are copied to
`audit_archive` and the source row is preserved. Removing rows
from the middle of the chain is unrecoverable, so the daemon
never deletes. See [docs/security.md](../security/security.md#audit-chain).
